Overview & Architecture

aioslsk is a pure-asyncio client implementation of the SoulSeek peer-to-peer file-sharing protocol (version 157, minor 100 — client.py:39-40). It speaks the three SoulSeek wire protocols (server, peer, distributed), manages chat rooms, user tracking, searches, shares and file transfers, and exposes everything through a single asyncio facade class. The package version is v1.6.3 (__init__.py:1). It is licensed as a library: there is no daemon or main loop of its own beyond run_until_stopped(); the embedding application owns the event loop.

The design is built around four cross-cutting primitives that every component receives by constructor injection:

  • Settings — a Pydantic BaseSettings tree (settings.py:181) holding all configuration (credentials, network, searches, shares, rooms, users, interests, transfers, debug). All sub-models use validate_assignment=True, so mutating settings at runtime re-validates.
  • EventBus — a single shared pub/sub bus (events.py:118) used both for public events (consumed by the embedding app) and internal events (used between managers). Listeners are held as weak references (events.py:130-136) and dispatched in priority order (lower first, default 100).
  • Network — owns all sockets/connections and the message routing (network/network.py:160).
  • Session — created on successful login (session.py:7-19); None until logged in and reset to None on server disconnect.

What is aioslsk & its asyncio design

Everything is coroutine-based. The client never blocks the loop: blocking work (file scanning, file I/O during transfers) is offloaded to an Executor via an injectable ExecutorFactory (shares/manager.py:48, client.py:55). Periodic work is expressed as BackgroundTask objects (tasks.py:17) — a coroutine plus an interval (which may itself be a callable, re-resolved each loop, tasks.py:41-45); the runner re-schedules using the value the coroutine returns, or the configured interval if it returns None (tasks.py:65-75). One-shot/re-schedulable delays use Timer (tasks.py:78). Examples of background tasks: server ping (server.py:24-29), user management (user/manager.py:122-130), UPnP renewal and the server-connection watchdog (network/network.py:194-204).

The fork installs a custom asyncio exception handler (client.py:117 → client.py:214-224): expected P2P churn (NetworkError, ConnectionError, TimeoutError, CancelledError) is logged at debug without a traceback; genuinely unexpected exceptions still get a full traceback (client.py:223-224). This is a soulshelf-fork log-noise reduction.

Eight managers are collected into self.services (client.py:84-93), the list the lifecycle iterates over. distributed_network is deliberately NOT in services: it is a BaseManager too (distributed.py:72) but it is driven entirely by events (PeerInitializedEvent, SessionInitializedEvent, SessionDestroyedEvent at distributed.py:107-117), so it has no explicit load_data()/start() call — only its stop() is reached, and only indirectly is it never iterated by the service loops. Be aware of this asymmetry when adding new distributed behaviour.

Finally the constructor builds the _MESSAGE_MAP via build_message_map(self) (client.py:95, helper at events.py:106-113) and registers two internal listeners (client.py:101-105): ConnectionStateChangedEvent → destroys the session on server CLOSED (client.py:376-382), and ServerReconnectedEvent → auto re-login when network.server.reconnect.auto is set (client.py:384-387).

Client lifecycle

The canonical sequence is start() → connect() → login() → run_until_stopped() → stop(). start(connect=True) can also do the connect step for you; __aenter__/__aexit__ wrap start()/stop() for async with usage (client.py:226-231).

  • start(connect=True) (client.py:107-130): installs the loop exception handler, creates self._stop_event, then gathers load_data() across all services followed by gathering start() across all services. If shares.scan_on_start is set it fires a shares scan task (client.py:126-127). If connect it calls connect().
  • connect() (client.py:158-162): delegates to network.initialize() (network/network.py:235-243) which opens the listening ports then connects the server connection.
  • login() (client.py:164-212): sends Login.Request, blocks on receive_message_object() for the Login.Response, raises AuthenticationError on failure (client.py:190-194), constructs the Session, emits SessionInitializedEvent, and only then starts the server reader loop (client.py:212). Login is therefore synchronous request/response, distinct from the post-login async reader.
  • run_until_stopped() (client.py:132-136): awaits self._stop_event; raises if the client was never started.
  • stop() (client.py:138-156): sets the stop event, network.disconnect() (cancels connection tasks & closes all connections, network/network.py:296-309), calls stop() on each service collecting cancelled tasks, awaits them, then store_data() on each service (writes the transfer + shares caches).

Command & event patterns

Outbound actions use the Command pattern. client.execute(command, response=False, timeout=10) (alias client(command) via __call__, client.py:233-237) requires a live session else raises InvalidSessionError (client.py:273-274). Each BaseCommand (commands.py:104, generic over RC=response-message / RT=return-type, commands.py:73-75) implements send(), build_expected_response() and handle_response() (commands.py:107-113). When response=True, execute registers an ExpectedResponse future (network/network.py:103) with the network, sends, and awaits the future under an async_timeout (client.py:276-291) — the SoulSeek protocol often sends no error reply, so commands that wait may legitimately time out.

Inbound state flows through events. The EventBus.emit (events.py:156-173) supports both async and sync listeners and swallows+logs listener exceptions so one bad listener cannot break dispatch. There is also a non-blocking emit_sync for sync-only listeners (events.py:175-194). Internal vs public events are distinguished by the InternalEvent marker base (events.py:618); examples of internal events: ConnectionStateChangedEvent, MessageReceivedEvent, PeerInitializedEvent, ServerReconnectedEvent, ScanCompleteEvent (events.py:622-682).

Wire Protocol & Message Framing

aioslsk speaks the SoulSeek protocol over four logical "planes" of TCP connections: the server connection, and three flavours of peer connection (peer, distributed, file). Every value on the wire is little-endian (all struct.Struct formats are prefixed with <, e.g. primitives.py:87, primitives.py:115). Messages are length-prefixed: a 4-byte uint32 length, followed by a per-plane message code and the payload. The two source-of-truth files are protocol/primitives.py (the (de)serialization machinery) and protocol/messages.py (~2254 lines of message definitions); framing on the wire is driven by network/connection.py.

Frame Layout on the Wire

A complete frame is header + message as assembled in DataConnection._read_message (connection.py:374). The length prefix counts everything after itself: the message code plus payload. Serialization computes it as uint32(len(message_id) + len(message)) in MessageDataclass.serialize_into (primitives.py:409).

The width of the message code differs by plane. Server and peer messages use a 4-byte uint32 code; peer-initialization and distributed messages use a 1-byte uint8 code. This is encoded in each message's MESSAGE_ID type and re-read during dispatch:

The file plane (PeerConnectionType.FILE = 'F', connection.py:55) carries no length-prefixed messages during transfer. After the peer-init handshake, a file connection exchanges a bare 4-byte uint32 ticket (receive_transfer_ticket, connection.py:648), then a bare 8-byte uint64 offset (receive_transfer_offset, connection.py:666), then a raw byte stream of file data (receive_file/send_file, connection.py:705, connection.py:739) with no framing at all.

Primitive Types

Each primitive is a thin subclass of int/str/bytes with a fixed struct.Struct (all little-endian) and three methods: serialize() -> bytes, serialize_into(buffer), and a classmethod deserialize(pos, data) -> (new_pos, value). ProtocolDataclass / MessageDataclass

ProtocolDataclass (primitives.py:259) is the generic (de)serialization engine. Subclasses are declared @dataclass(order=True) with one field(metadata={'type': <primitive>, ...}) per wire field; field declaration order is the wire order. The engine caches dataclasses.fields() in _CACHED_FIELDS (primitives.py:275, populated at primitives.py:290/317) to avoid repeated reflection.

Field metadata keys controlling (de)serialization (documented in the module docstring, primitives.py:3-31):

  • 'type' — the primitive class. Missing it raises Exception("no 'type' for field …") (primitives.py:301, 327).
  • 'subtype' — element type for array fields (primitives.py:305, 331).
  • 'if_true' / 'if_false' — conditional: only (de)serialize this field when the named sibling field is truthy/falsy (primitives.py:345-351 on deserialize; primitives.py:366-372 on serialize). Used heavily in Login.Response where greeting/ip/md5hash/privileged are gated on if_true: 'success' and reason on if_false: 'success' (messages.py:149-153).
  • 'optional' — trailing field that is only deserialized if unparsed bytes remain (pos < len(message), primitives.py:353-354) and only serialized if its value is not None (primitives.py:362-364). Example: the trailing obfuscated-port fields on SetListenPort/GetPeerAddress (messages.py:169-170, 195-196).

MessageDataclass (primitives.py:377) extends this to add the on-wire frame. It carries MESSAGE_ID: ClassVar[Union[uint8, uint32]] (primitives.py:384). serialize_into (primitives.py:399): serializes the message id, serializes the body via the parent into a separate buffer, optionally zlib-compresses the body, then writes uint32(len(message_id)+len(message)) followed by id and body. deserialize (primitives.py:413): reads-and-discards the length, reads the message id via type(cls.MESSAGE_ID).deserialize (so uint8 vs uint32 is automatic), and raises ValueError on id mismatch (primitives.py:429-430). After parsing the body it warns if trailing bytes remain (primitives.py:439-443) — this is the one remaining stock logger.warning in primitives, not downgraded by the fork.

Request/Response & Code Dispatch

messages.py declares one outer class per logical message (e.g. Login, messages.py:119), inheriting a marker base (ServerMessage / PeerInitializationMessage / PeerMessage / DistributedMessage). Inside it nests Request and/or Response dataclasses, each a MessageDataclass with its own MESSAGE_ID. The docstring (messages.py:1-18) spells out the convention: server messages have both directions (client sends Request, receives Response, often sharing the same id, e.g. Login id 0x01 for both, messages.py:138/147); peer/distributed messages are Request-only.

Dispatch from raw bytes to a typed object is a linear scan over __subclasses__() matching on MESSAGE_ID. For example ServerMessage.deserialize_response (messages.py:62) reads the uint32 code at offset 4, then iterates marker subclasses looking for one whose .Response.MESSAGE_ID matches, calling response_cls.deserialize(0, message). No match raises UnknownMessageError(msg_id, message, ...) (messages.py:71, defined exceptions.py:28). The four entry points are deserialize_request/deserialize_response (server) and deserialize_request (the three peer planes).

Code-width by plane is fixed in the dispatch: server/peer read uint32 (messages.py:53,64,94); peer-init/distributed read uint8 (messages.py:79,109). A few example codes: server Login=0x01, GetPeerAddress=0x03, ConnectToPeer=0x12, FileSearch=0x1A; peer-init PeerPierceFirewall=0x00 (messages.py:1817), PeerInit=0x01 (messages.py:1845); peer PeerSharesReply=0x05 (messages.py:1897), PeerSearchReply=0x09 (messages.py:1942); distributed DistributedSearchRequest=0x03 (messages.py:2188), DistributedBranchLevel=0x04 (messages.py:2204).

Two quirks worth noting for an agentic coder: PeerInit.ticket uses a custom _PeerInitTicket(uint32) type (messages.py:1821) that falls back to uint64 when more than 4 bytes remain, because some clients send a 64-bit ticket. And DistributedServerSearchRequest is a distributed message yet declares a uint32 MESSAGE_ID = 0x5D (messages.py:2249) — a deprecated wrapper that should be translated to a real DistributedSearchRequest.

Obfuscation

The protocol supports an obfuscated transport (a rolling-key XOR cipher) implemented in protocol/obfuscation.py. Key facts:

  • KEY_SIZE = 4 (obfuscation.py:6). An obfuscated frame prepends a 4-byte plaintext key, so HEADER_SIZE_OBFUSCATED = KEY_SIZE + struct.calcsize('I') = 8 vs HEADER_SIZE_UNOBFUSCATED = 4 (connection.py:50-51).
  • encode(data, key=None) (obfuscation.py:68) generates a random key if none given, rotates the key right by 31 bits every KEY_SIZE bytes, XORs the stream, and returns orig_key + enc_message (obfuscation.py:85).
  • decode(data) (obfuscation.py:42) takes the leading 4 bytes as the key, builds a key array by rotating right from bit 31 downward for up to 32 blocks (obfuscation.py:54-58), then XOR-unmasks. Note: decode and encode use subtly different key-schedule loops, but they round-trip.

Where obfuscation is toggled: the flag lives on the connection as obfuscated (set in DataConnection.__init__, connection.py:199). On send, encode_message_data calls obfuscation.encode(data) only if self.obfuscated (connection.py:524-525); on receive, _read_message de-obfuscates just the header to find the length (connection.py:383) and decode_message_data de-obfuscates the whole frame (connection.py:537-538). Critically, PeerConnection.set_connection_state (connection.py:620) forces obfuscated = False for any non-PEER connection (distributed and file) once it leaves AWAITING_INIT (connection.py:634-636) — so only the server plane and message-type peer connections ever stay obfuscated. The network layer decides the initial flag per connection (network.py:225 server-plain, network.py:231 server-obfuscated, and per-peer at network.py:830/922).

Compression (zlib)

Compression is per-message and uses zlib (imported at primitives.py:48). It is wired through the compress/decompress flags of MessageDataclass.serialize_into (primitives.py:406-407: zlib.compress(message)) and MessageDataclass.deserialize (primitives.py:433-435: zlib.decompress(message[pos:]) then parse from offset 0). Only the payload is compressed — the length prefix and message id stay plaintext (primitives.py:406-411).

A message opts in by overriding both methods to pass the flag as default True. The compressed messages in this fork are all heavy peer payloads:

Connection Read/Parse/Serialize Path

The receive loop is DataConnection._message_reader_loop (connection.py:297), started once a connection reaches ESTABLISHED (connection.py:641-642). It repeatedly calls receive_message_object (connection.py:398) which: (1) reads a full raw frame via receive_message → _read(self._read_message(), timeout=read_timeout) (connection.py:390-396); (2) decodes it via decode_message_data (connection.py:529) — de-obfuscate if needed, then deserialize_message; (3) dispatches to the network via _perform_message_callback (connection.py:566).

_read_message (connection.py:374) is the framing core: it reads exactly header_size bytes, de-obfuscates the header if obfuscated to recover the length, reads exactly message_len more bytes via readexactly, and returns header + message. Plane selection happens in deserialize_message: ServerConnection always uses ServerMessage.deserialize_response (connection.py:590-591); PeerConnection (connection.py:758) routes to PeerInitializationMessage while in AWAITING_INIT, else to PeerMessage (type PEER) or DistributedMessage (otherwise).

Send path: send_message (connection.py:476) skips silently if the connection is closing (fork-downgraded to debug, connection.py:486-491), serializes via encode_message_data → serialize_message (which calls message.serialize() for a MessageDataclass or passes raw bytes through, connection.py:553-557), obfuscates if needed, and writes with a 10s drain timeout (connection.py:509). Messages can be fire-and-forget queued via queue_message (connection.py:440).

Deserialize Error Path & Fork Downgrade

decode_message_data wraps any deserialization failure into a MessageDeserializationError(data, "failed to deserialize message") (connection.py:540-543; defined exceptions.py:40, carrying the raw proto_message bytes). The serialize counterpart is MessageSerializationError (exceptions.py:36). The read loop catches three failure classes distinctly (connection.py:305-313):

  • ConnectionReadError — peer dropped mid-read; loop logs and continues.
  • MessageDeserializationError — a peer sent unparseable bytes; loop logs exc.proto_message and continues (does not tear down the connection).
  • otherwise (success) — if message is falsy the loop returns (EOF); else dispatches.

Worked (De)serialization Example

Building a server GetPeerAddress.Request (code 0x03, single string field) for user "abc" and inspecting the frame:

from aioslsk.protocol.messages import GetPeerAddress

msg = GetPeerAddress.Request(username="abc")
frame = msg.serialize()          # MessageDataclass.serialize -> serialize_into  (primitives.py:386)
# frame bytes, all little-endian:
#   length : 0x0B 00 00 00   -> uint32(11)  = len(code=4) + len(payload=7)
#   code   : 0x03 00 00 00   -> uint32(0x03)  (server plane = uint32, messages.py:186)
#   payload: 0x03 00 00 00   -> string length prefix uint32(3)
#            0x61 0x62 0x63   -> b"abc"
assert frame == bytes.fromhex("0b000000" "03000000" "03000000" "616263")

# Round-trip via the dispatcher (reads code at offset 4, scans subclasses):
from aioslsk.protocol.messages import ServerMessage
parsed = ServerMessage.deserialize_request(frame)   # messages.py:51
assert isinstance(parsed, GetPeerAddress.Request)
assert parsed.username == "abc"

For PeerSearchReply.Request (code 0x09), serialize() defaults compress=True (messages.py:1959), so MessageDataclass.serialize_into runs zlib.compress over the body before the length prefix is computed (primitives.py:406-409); on the way back deserialize defaults decompress=True (messages.py:1962) and zlib.decompresses from just past the id before parsing the results: array[FileData] field (primitives.py:433-435).

Server Connection & Server Messages

aioslsk maintains exactly one long-lived TCP connection to the central SoulSeek server. That connection is the control plane for the whole client: it carries the login session, resolves peer addresses, brokers indirect (firewall-pierce) peer connections, distributes search queries, and streams user/room/privilege state changes. All peer-to-peer file transfer happens on separate PeerConnections, but every one of them is bootstrapped through the server. This section documents how the single ServerConnection is established, authenticated, kept alive, advertised, and reconnected, and tabulates the server messages an integrator actually touches.

Overview & topology

The server connection object is created once in the Network constructor and stored as a public attribute network.server_connection (network/network.py:171), built by create_server_connection from the configured hostname/port (network/network.py:212-217). It is a ServerConnection(DataConnection) whose only job beyond the generic data-connection machinery is to deserialize incoming frames with the server message registry: ServerMessage.deserialize_response(message_data) (network/connection.py:590-591).

Lifecycle ownership is split across three classes:

  • Network (network/network.py:160) owns the socket, the listening-port advertisement, and the reconnect watchdog.
  • SoulSeekClient (client.py) performs the login() handshake and owns the Session object, emitting SessionInitializedEvent / SessionDestroyedEvent.
  • ServerManager (server.py:16) is a thin manager driving the periodic keep-alive Ping — it starts a BackgroundTask on ConnectionState.CONNECTED and cancels it on CLOSING (server.py:54-62), pinging every SERVER_PING_INTERVAL = 5 * 60 seconds (constants.py:22, server.py:24-29).

Connecting to the server

The defaults point at the public SoulSeek server: hostname = 'server.slsknet.org', port = 2416 (settings.py:56-58). Connection is kicked off by Network.initialize(), which first opens the listening ports and then connects the server socket (network/network.py:235-240):

async def initialize(self):
    await self.connect_listening_ports()
    await self.connect_server()

connect_server() delegates to self.server_connection.connect() (network/network.py:290-291), which uses a 30-second connect timeout (SERVER_CONNECT_TIMEOUT = 30, constants.py:20; network/connection.py:587-588). The connection read timeout is SERVER_READ_TIMEOUT = SERVER_PING_INTERVAL * 2 = 600s (constants.py:23, network/connection.py:581) — i.e. two missed ping cycles before the read loop treats the link as dead.

When the server socket reaches ConnectionState.CONNECTED, Network._on_server_connection_state_changed fires (network/network.py:1031-1044): it starts the UPnP port-mapping job if network.upnp.enabled, and starts the reconnect watchdog if network.server.reconnect.auto is set. Note that opening the socket does not log you in — the async reader loop is deliberately not started until after a successful login (see below).

Connection states are UNINITIALIZED, CONNECTING, CONNECTED, CLOSING, CLOSED (network/connection.py:60-65); close reasons are UNKNOWN, CONNECT_FAILED, REQUESTED, READ_ERROR, WRITE_ERROR, TIMEOUT, EOF (network/connection.py:68-75). Every state transition flows through set_state → network.on_state_changed (network/connection.py:105-108), which both dispatches the server/peer-specific handler and emits a ConnectionStateChangedEvent (network/network.py:1021-1029).

Login handshake (Login.Request / Login.Response, client_version 157)

Login is driven by SoulSeekClient.login() (client.py:164-212). It sends a single Login.Request, then reads exactly one message off the raw socket and asserts it is a Login.Response:

await self.network.send_server_messages(
    Login.Request(
        username=username,
        password=password,
        client_version=client_version,        # CLIENT_VERSION = 157
        md5hash=calc_md5(username + password), # MD5 of username+password concatenated
        minor_version=minor_version            # MINOR_VERSION = 100
    )
)
response = await self.network.server_connection.receive_message_object()
if not isinstance(response, Login.Response):
    raise AioSlskException(...)
if not response.success:
    raise AuthenticationError(response.reason if response.reason else '', ...)

The version constants are module-level in client.py: CLIENT_VERSION = 157 and MINOR_VERSION = 100 (client.py:39-40), used as the defaults of login() (client.py:165). The request md5hash is the MD5 of username + password concatenated (client.py:180, via protocol.primitives.calc_md5); the message docstring notes the response md5hash is instead the hash of the password alone (protocol/messages.py:123-126).

Login.Request wire fields are username, password, client_version, md5hash, minor_version (message id 0x01, protocol/messages.py:136-143). Login.Response (also 0x01) carries success: bool and, only when successful, greeting, ip (your own external IP as the server sees it), md5hash, and privileged; on failure it carries reason (protocol/messages.py:145-153).

On success the client builds a Session (session.py:7-19) from the response — capturing ip_address, greeting, client_version, minor_version, a logged_in_at timestamp, and privileges_time_left — emits SessionInitializedEvent, and only then starts the server reader task (client.py:197-212):

self.session = Session(
    user=self.users.get_user_object(username),
    ip_address=response.ip if response.ip is not None else '',
    greeting=response.greeting if response.greeting is not None else '',
    client_version=client_version,
    minor_version=minor_version
)
await self.events.emit(SessionInitializedEvent(session=self.session, raw_message=response))
# Finally start up the reader loop for the server
self.network.server_connection.start_reader_task()

This ordering matters for integrators: the synchronous read of the Login.Response bypasses the normal message-dispatch loop, so no handlers run for it; the asynchronous reader (and therefore all server-message events) only begins after SessionInitializedEvent. A failed login raises AuthenticationError with the server's reason (client.py:190-194).

Session events & listening-port advertisement

SessionInitializedEvent (events.py:227-231) carries the session: Session and the raw raw_message: Login.Response. It is the central fan-out point: the user, room, interest, transfer, and distributed managers all register a _on_session_initialized listener (e.g. distributed.py:115, room/manager.py:132, interest/manager.py:53, transfer/manager.py:136), and the Network itself listens (network/network.py:208-210).

The Network handler advertises the listening ports immediately after login (network/network.py:1167-1168):

async def _on_session_initialized(self, event: SessionInitializedEvent):
    await self.advertise_listening_ports()

advertise_listening_ports() reads the currently connected ports via get_listening_ports() (which returns 0 for any port not in ConnectionState.CONNECTED, network/network.py:313-327) and sends a SetListenPort request (network/network.py:329-339):

async def advertise_listening_ports(self):
    port, obfuscated_port = self.get_listening_ports()
    await self.send_server_messages(
        SetListenPort.Request(
            port,
            obfuscated_port_amount=1 if obfuscated_port else 0,
            obfuscated_port=obfuscated_port
        )
    )

This tells the server which TCP port(s) other peers should use to make a direct connection back to this client. Default ports are network.listening.port = 60000 and network.listening.obfuscated_port = 60001 (settings.py:62-65). The non-obfuscated port is load-bearing: with error_mode = CLEAR (the default, settings.py:63), connect_listening_ports only raises if the non-obfuscated port fails to bind (network/network.py:274-277). The other error modes are ALL (raise only if every port failed) and ANY (raise if any failed) (network/network.py:78-90, 264-272).

SessionDestroyedEvent (events.py:234-239) is emitted by the client when the server connection reaches ConnectionState.CLOSED while a session exists; the client nulls out self.session first, so listeners observe an already-torn-down session (client.py:376-382):

async def _on_connection_state_changed(self, event):
    if isinstance(event.connection, ServerConnection):
        if event.state == ConnectionState.CLOSED:
            if session := self.session:
                session_event = SessionDestroyedEvent(session)
                self.session = None
                await self.events.emit(session_event)

What the server is used for

  • Peer address resolution. Before making a direct peer connection, Network._get_peer_address(username) sends GetPeerAddress.Request and awaits the matching GetPeerAddress.Response (network/network.py:625-647). A response of ip == '0.0.0.0' means the user is offline/unknown; no valid ports means the peer is unreachable — both raise PeerConnectionError (network/network.py:639-645). The resolved (ip, port, obfuscated_port) then feeds _make_direct_connection (network/network.py:806-817).
  • Indirect-connection brokering. When a direct connection can't be made (NAT/firewall), the client sends ConnectToPeer.Request(ticket, username, typ) to the server, which relays it; the peer then pierces our firewall (network/network.py:850-880). Conversely, when another peer wants to reach us, the server sends a ConnectToPeer.Response, handled by _on_connect_to_peer which spawns a task to call us back (network/network.py:794-804). (soulshelf fork: the failure path in _handle_connect_to_peer_callback logs at debug rather than warning — a NAT'd/leech-only client cannot fulfil most callbacks and the warning flooded the log; network/network.py:1177-1179.)
  • Search distribution. Outgoing searches are sent to the server as FileSearch.Request (global), RoomSearch.Request, or UserSearch.Request (search/manager.py:125,149,173); wishlist searches use WishlistSearch.Request at the server-dictated interval (search/manager.py:286). Incoming searches from other users arrive as ServerSearchRequest (to be forwarded to distributed children, protocol/messages.py:1119-1133) or, for room/user-targeted searches, as a FileSearch.Response.
  • User / room / privilege state. The server pushes status and stats for tracked users (added via AddUser) and for users sharing a room, via GetUserStatus, GetUserStats, UserJoinedRoom/UserLeftRoom, plus RoomList, PrivilegedUsers, and WishlistInterval after logon.
  • Distributed-network parameters. After logon the server sends ParentMinSpeed, ParentSpeedRatio, MinParentsInCache, DistributedAliveInterval, and PotentialParents to drive the distributed search overlay.
  • Keep-alive. The ServerManager sends Ping.Request every 5 minutes (server.py:41-43).

Automatic reconnection is opt-in. The relevant settings live under network.server.reconnect: auto: bool = False and timeout: int = 10 seconds (settings.py:51-53). It is started only when the server reaches CONNECTED with reconnect.auto true (network/network.py:1043-1044), and stopped explicitly when the connection closes on request or by EOF (network/network.py:1063-1069).

async def _server_connection_watchdog_job(self, context):
    timeout = self._settings.network.server.reconnect.timeout
    if self.server_connection.state == ConnectionState.CLOSED:
        if not self._settings.credentials.are_configured():
            ...  # log once, do not reconnect
            return
        else:
            logger.info("will attempt to reconnect to server in %d seconds", timeout)
            await asyncio.sleep(timeout)
            try:
                await self.connect_server()
            except ConnectionFailedError:
                logger.warning("failed to reconnect to server")
            else:
                await self._event_bus.emit(ServerReconnectedEvent())
    context.last_state = self.server_connection.state

Key behaviours an integrator must know:

  • The watchdog only acts when the socket is in CLOSED — the CLOSING handler decides beforehand whether reconnect should even be attempted (network/network.py:1046-1069).
  • EOF means stop. If the server sends EOF (CloseReason.EOF) — which happens when your IP is banned for opening too many connections, or you are kicked due to a duplicate login — the watchdog is cancelled and no reconnect is attempted (network/network.py:1066-1069). The inline comment warns that reconnecting while banned only extends the ban.
  • A successful reconnect emits ServerReconnectedEvent (network/network.py:400-401), which the client handles by automatically re-running login() if reconnect.auto is set (client.py:384-387). Reconnect therefore re-drives the full handshake → SessionInitializedEvent → re-advertise ports chain.
  • If credentials are not configured, the watchdog logs a single warning and gives up (network/network.py:384-390).

Peer Connections & the Connect Algorithm

Every interaction with another SoulSeek user that is not relayed through the central server happens over a peer connection: a raw TCP socket between two clients, opened on demand and torn down freely. The hard part of SoulSeek is that either end may be behind NAT, so the protocol defines two complementary ways to establish the same logical connection — a direct outbound dial and an indirect "ask the server to make them dial me back" handshake — and aioslsk can run them sequentially (FALLBACK) or simultaneously (RACE). All of this lives in network/network.py and network/connection.py. The single public entry point is Network.create_peer_connection (network/network.py:522), with Network.get_peer_connection (network/network.py:649) layered on top for reuse.

  • Message framing on read.   • Obfuscation. Only 'P' connections may stay obfuscated. PeerConnection.set_connection_state (network/connection.py:620) forces self.obfuscated = False for any non-PEER connection the moment it leaves AWAITING_INIT (:634).

The username/typ in PeerInit are how the receiving side learns who connected and for what — see on_peer_accepted below.

The outbound sender writes its init message in code. For a direct connection, _make_direct_connection sends PeerInit.Request(self._settings.credentials.username, typ, ticket) right after connection.connect() (network/network.py:835). For an indirect callback, _handle_connect_to_peer sends PeerPierceFirewall.Request(message.ticket) (network/network.py:930).

The inbound receiver reads the first object via on_peer_accepted (network/network.py:1079). Its branching is the protocol:

  • PeerInit.Request → copy username and typ onto the connection, finalise, emit PeerInitializedEvent(connection, requested=False) (:1113). This is an unsolicited inbound peer.
  • PeerPierceFirewall.Request → look up self._expected_connection_futures[ticket] (:1124); on hit, copy the username/typ stored in the waiting PeerFuture, finalise, emit PeerInitializedEvent(..., requested=True), then connection_future.set_result(connection) to wake the _make_indirect_connection coroutine (:1131–1139). On an unknown ticket it logs a warning and disconnects (:1125).
  • Anything else → warn and disconnect (:1141).

Finalisation is centralised in _finalize_peer_connection (network/network.py:947): an 'F' connection transitions to PeerConnectionState.NEGOTIATING_TRANSFER and gets the shared up/download rate limiters attached; every other type transitions straight to PeerConnectionState.ESTABLISHED. Reaching ESTABLISHED is what starts the background message reader loop (set_connection_state → start_reader_task, network/connection.py:641). For 'F' connections there is no reader loop — the transfer code drives the socket synchronously with receive_transfer_ticket/receive_transfer_offset/receive_file (network/connection.py:648,666,705).

Direct vs Indirect connections

Direct (_make_direct_connection, network/network.py:806): we open the socket ourselves. If ip/port were not supplied, we ask the server with GetPeerAddress.Request(username) and await the matching GetPeerAddress.Response (_get_peer_address, :625). The response's ip, port and obfuscated_port feed select_port (:817, see settings). A 0.0.0.0 IP or no usable port raises PeerConnectionError (:639–645). We then construct a PeerConnection, append it to self.peer_connections, connect(), send PeerInit, finalise, and emit PeerInitializedEvent(connection, requested=True). Direct only works if the peer is reachable inbound from us — i.e. they are not firewalled.

Indirect (_make_indirect_connection, network/network.py:850): when we cannot reach the peer directly (typically because they are firewalled), we ask the server to relay a request asking them to connect back to us. The steps:

  1. Register a PeerFuture(ticket, username, typ) in self._expected_connection_futures[ticket] (:865–869) — this is the slot on_peer_accepted will later resolve when the peer's PeerPierceFirewall arrives.
  2. Register a server-response future for CannotConnect.Response filtered on ticket (:871).
  3. Send ConnectToPeer.Request(ticket, username, typ) to the server (:879).
  4. asyncio.wait on both futures with FIRST_COMPLETED and a PEER_INDIRECT_CONNECT_TIMEOUT (60 s) deadline (:883).

Outcomes: empty done → timeout → PeerConnectionError (:893); the CannotConnect future completed → the server told us the peer could not connect back → PeerConnectionError (:899); otherwise the PeerFuture resolved and we return its PeerConnection result (:903). Indirect succeeds only if we are reachable inbound — the peer must be able to open a socket to one of our listening ports.

The mirror image — fulfilling someone else's indirect request. When the server forwards a ConnectToPeer.Response to us, _on_connect_to_peer (network/network.py:794) spawns _handle_connect_to_peer (:905) as a tracked task. That coroutine dials out to the requester's ip/port, sends PeerPierceFirewall.Request(message.ticket), finalises, and emits PeerInitializedEvent(..., requested=False). If our outbound dial fails (NetworkError), we tell the server CannotConnect.Request(ticket, username) and raise (:933–940) — which is exactly the CannotConnect.Response the original requester is waiting on.

The weakref gotcha (critical for integrators)

This is the single most common footgun. register does not hold a strong reference to your listener. It stores either a weakref.ref (for plain functions) or a weakref.WeakMethod (for bound methods), chosen at events.py:130-133:

ref_factory: type[weakref.ReferenceType] = weakref.ref
if isinstance(listener, MethodType):
    ref_factory = weakref.WeakMethod
entry = (
    priority,
    ref_factory(listener, lambda ref: self._remove_callback(event_class, ref))
)

The callback passed to the weakref (_remove_callback, events.py:211) automatically purges the entry the moment the referent is garbage-collected. Consequences:

  • A lambda or local def registered inline and not stored anywhere is collected almost immediately and silently stops firing. bus.register(SearchResultEvent, lambda e: print(e)) will likely never fire.
  • A bound method of an object you don't keep a reference to (e.g. bus.register(Event, SomeHandler().on_event) where the SomeHandler() instance is discarded) is collected because WeakMethod doesn't keep the instance alive.
  • At dispatch, _get_listeners_for_event (events.py:196) dereferences each weakref and skips any that returned None — so a GC'd listener just quietly disappears with no error.

How to keep listeners alive: store a strong reference for the lifetime you want callbacks. Either keep your handler object as an attribute on something long-lived, or assign the function to a variable that outlives the bus usage:

# WRONG - GC'd, never fires
client.events.register(SearchResultEvent, lambda e: handle(e))

# RIGHT - method on an object you retain
class MyApp:
    def __init__(self, client):
        self._client = client
        client.events.register(SearchResultEvent, self.on_result)  # self kept by you
    def on_result(self, event: SearchResultEvent): ...

# RIGHT - keep the function reference
self._cb = lambda e: handle(e)
client.events.register(SearchResultEvent, self._cb)

The library's own managers register bound methods and survive only because the manager instances are held by the client (e.g. SharesManager.register_listeners at shares/manager.py:172-176 registers self._on_session_initialized, and the manager is owned by the client).

The SharesManager (shares/manager.py:146) indexes local directories so other users can browse, search, and download from you. If you only download, you can leave shares.directories empty and the manager simply reports zero shares.

Model. A SharedDirectory (shares/model.py:19) has directory, absolute_path, an alias (a 5-char obfuscated id generated from the path mixed with the machine's hardware address, generate_alias at shares/manager.py:182), a share_mode, an allowed users list, and a set of SharedItems. Each SharedItem (shares/model.py:80) holds subdir, filename, modified mtime, and optional audio attributes. Remote paths use the form @@<alias>\Music\song.mp3 (get_remote_path, shares/model.py:98-104) — backslash-separated, alias-prefixed, so the real local layout is never leaked.

Share modes (DirectoryShareMode, shares/model.py:10): EVERYONE, FRIENDS, USERS. Locking is resolved in is_directory_locked (shares/manager.py:918): FRIENDS locks anyone not in settings.users.friends; USERS locks anyone not in the directory's own users list; EVERYONE never locks. Queries and browse replies split results into visible vs locked accordingly (query at shares/manager.py:653, create_shares_reply at shares/manager.py:799).

Indexing. load_data (shares/manager.py:227) reads the cache then load_from_settings (shares/manager.py:234) reconciles shares.directories against the in-memory list (adds new, updates existing, drops removed) and calls rebuild_term_map. scan() (shares/manager.py:621) walks each directory on an executor (scan_directory, shares/manager.py:64), extracts audio metadata via mutagen (extract_attributes, shares/manager.py:108), emits a ScanCompleteEvent, and calls report_shares() to send the folder/file counts to the server (SharedFoldersFiles.Request, shares/manager.py:931-943). How queries match. Incoming peer searches are answered by query() (shares/manager.py:653). It first parses the query into a SearchQuery with include/exclude/wildcard terms (search/model.py:35-60), then does a fast first pass against an inverted index, the _term_map — a dict[str, WeakSet[SharedItem]] built by splitting each item's subdir/filename on the non-word regex [\W_] and lower-casing (_add_item_to_term_map, shares/manager.py:883). Items must match every include term (set intersection, shares/manager.py:717-719); wildcard terms match map keys by suffix (shares/manager.py:701-705). Survivors are then filtered with per-term regex matchers and excluded phrases, capped at searches.receive.max_results (shares/manager.py:727-743). Because the term map uses WeakSet, items dropped from a directory disappear from the index automatically; _cleanup_term_map (shares/manager.py:894) prunes emptied entries.

Distributed Network & Search Propagation Algorithm

The distributed network is the mechanism by which Soulseek fans out search queries to the entire network without the central server having to push every query to every one of millions of users. Clients organise themselves into a search distribution tree: each client has at most one parent and up to _max_children children. A query enters the tree at a branch root (a client whose parent is the server itself), flows down from parent to children, and every client along the way queries its own shares. Crucially, results do not flow back up the tree — each matching client opens a direct peer connection back to the original searcher. The whole subsystem lives in distributed.py in the DistributedNetwork(BaseManager) class distributed.py:72.

Why a distributed search tree

If the server had to relay every search to every peer, fan-out cost would be O(users × searches) on a single machine. Instead the server only delivers a search to a small set of branch roots (and to clients it directly serves), and those roots replicate it down their subtrees. Each non-root client receives a query once from its parent and re-broadcasts it to its own children only. This turns server-side fan-out into a tree-amortised, peer-driven flood. The cost to the originating searcher is a single message to the server; the cost to the server is delivery to roots; everything else is paid for by the peers themselves. The ServerSearchRequest docstring states the contract directly: "Search request sent by another user through the server. Upon receiving this the message should be passed on to the distributed children" protocol/messages.py:1119-1124.

Search Subsystem

The search subsystem is what an integrator uses to ask the SoulSeek network "who has files matching this query?". It is implemented by SearchManager in search/manager.py, with data models in search/model.py and the wire types in protocol/primitives.py. The single most important thing to understand is that searches are fire-and-forget; results stream back asynchronously over an unbounded window of time. There is no await client.searches.search(...) that returns results — sending a query and receiving its results are two completely decoupled flows.

Overview & two entry points

There are two parallel ways to launch a search, and they do almost the same thing:

  • Manager methods — SearchManager.search(), .search_room(), .search_user() (search/manager.py:114, :136, :161). These are async, register the request, attach a timeout timer, emit SearchRequestSentEvent, and return the SearchRequest object so you can hold onto it.
  • Command objects — GlobalSearchCommand, UserSearchCommand, RoomSearchCommand (commands.py:548, :569, :593), executed via await client.execute(GlobalSearchCommand(query)) (client.py:239). These are typed BaseCommand[None, None] — they return None and do not attach a timeout timer, do not emit SearchRequestSentEvent, and do not give you back the SearchRequest (it is only stored into client.searches.requests[ticket]). They are thinner.

Recommendation for integrators: prefer the manager methods (client.searches.search(query)), because you get the SearchRequest handle back, you get timeout/lifecycle events, and the request is correctly tracked. The command variants exist for API symmetry but lose the request handle and the timer. Both share the same ticket generator behaviour and both write into the same requests dict, so results are matched identically.

Async results & the collection-window pattern

This is the crux of the subsystem. None of the search methods wait for or return results. Results arrive whenever remote peers feel like answering — typically over a span of seconds to minutes, and potentially never. Each reply is delivered through one of two mechanisms, both driven by _on_peer_search_reply() (search/manager.py:380-403):

@on_message(PeerSearchReply.Request)
async def _on_peer_search_reply(self, message, connection):
    search_result = SearchResult(
        ticket=message.ticket,
        username=message.username,
        has_free_slots=message.has_slots_free,
        avg_speed=message.avg_speed,
        queue_size=message.queue_size,
        shared_items=message.results,
        locked_results=message.locked_results or []
    )
    try:
        query = self.requests[message.ticket]
    except KeyError:
        logger.warning("search reply ticket does not match any search request : %d", message.ticket)
    else:
        if self._settings.searches.send.store_results:
            query.results.append(search_result)
        await self._event_bus.emit(SearchResultEvent(query, search_result))
    await connection.disconnect(reason=CloseReason.REQUESTED)

For each incoming PeerSearchReply the manager does two things: (1) appends the SearchResult to request.results (if storing is enabled) and (2) emits SearchResultEvent(query, result) on the event bus. A reply whose ticket is not in self.requests (e.g. after you removed the request, or after a timeout) is logged at warning and dropped — this is exactly how remove_request makes late results "ignored" (search/manager.py:104-112).

Because there is no terminating signal from the network, integrators use one of two patterns:

  • Event-driven (push): register a listener for SearchResultEvent on the client's event bus and react as each result lands. Signature: SearchResultEvent(query: SearchRequest, result: SearchResult) (events.py:489-493). Register via client.events.register(SearchResultEvent, handler) (events.py:125); the handler must be an async def.
  • Collection-window (poll): launch the search, sleep for a fixed window (e.g. await asyncio.sleep(15)), then read request.results — the list will contain whatever arrived during the window. This works because results are appended in-place into the same SearchRequest object you were handed. Pick the window length yourself; there is no library default for "how long to wait."

def get_attribute_map(self) -> dict[AttributeKey, int]:
    attribute_dict = {}
    for attr in self.attributes:
        try:
            attribute_dict[AttributeKey(attr.key)] = attr.value
        except ValueError:
            pass
    return attribute_dict

Practical heuristic for distinguishing format families: a result carrying BITRATE (and possibly VBR) is lossy (MP3); a result carrying SAMPLE_RATE and BIT_DEPTH is lossless (FLAC/WAV). Many peers omit attributes entirely, so always treat the map as sparse and default-missing.

Ranking. The library does not sort or de-duplicate results for you — that is the integrator's job. The signals available per candidate file are: SearchResult.avg_speed (peer throughput), SearchResult.has_free_slots (no queue wait), SearchResult.queue_size (shorter is better), and the per-file quality map. A typical composite key is "prefer free slots, then higher bitrate/lossless, then higher avg_speed, then smaller queue." See the recipe below for a concrete sort key.

remove_request & request lifecycle

A SearchRequest lives in SearchManager.requests: dict[int, SearchRequest] (search/manager.py:76) keyed by ticket. It can leave that dict three ways:

  • Manual removal — remove_request(request_or_ticket) (search/manager.py:104-112) does self.requests.pop(ticket). Accepts either a SearchRequest or a bare int ticket. After this, any further PeerSearchReply for that ticket misses the dict lookup and is logged-and-dropped (search/manager.py:394). It does not emit an event and does not cancel an attached timer — and note pop with no default will raise KeyError if the request was already gone.
  • Timeout removal — if a timer was attached (only when request_timeout > 0 for normal searches, or via the wishlist interval), it fires _timeout_search_request(request) which does del self.requests[ticket] and emits SearchRequestRemovedEvent (search/manager.py:327-329).
  • Never — with the default request_timeout = 0 and no manual cleanup, a request stays in requests indefinitely and keeps accepting late results. For long-lived clients you should call remove_request once you have closed your collection window, to bound memory growth in requests and in each request's results list.

    # 1) Launch the search; you get the SearchRequest handle back immediately.
    #    Results are NOT returned here -- they stream in asynchronously.
    request = await client.searches.search(query)

    # 2) Collection window: let peers reply for `window` seconds.
    #    request.results is filled in-place as SearchResultEvents fire.
    await asyncio.sleep(window)

    # 3) Flatten (SearchResult per peer) -> (peer, file) candidates.
    candidates = []
    for result in request.results:
        for file in result.shared_items:          # .locked_results for private hits
            attrs = file.get_attribute_map()       # dict[AttributeKey, int]
            candidates.append({
                'username':   result.username,      # download key, with filename
                'filename':   file.filename,
                'filesize':   file.filesize,
                'free_slots': result.has_free_slots,
                'avg_speed':  result.avg_speed,     # bytes/sec
                'queue_size': result.queue_size,
                'bitrate':    attrs.get(AttributeKey.BITRATE),     # kbps or None
                'is_vbr':     bool(attrs.get(AttributeKey.VBR, 0)),
                'duration':   attrs.get(AttributeKey.DURATION),    # seconds or None
                'samplerate': attrs.get(AttributeKey.SAMPLE_RATE), # Hz or None (FLAC)
                'bit_depth':  attrs.get(AttributeKey.BIT_DEPTH),   # bits or None (FLAC)
            })

    # 4) Rank: prefer free slots, then quality, then faster peers, then shorter queue.
    #    sorted() is ascending, so negate the "higher is better" signals.
    candidates.sort(key=lambda c: (
        not c['free_slots'],                 # free slots first
        -(c['bitrate'] or 0),                # higher bitrate first
        -(c['avg_speed'] or 0),              # faster peer first
        c['queue_size'],                     # shorter queue first
    ))

    for c in candidates[:20]:
        speed_kib = c['avg_speed'] / 1024
        if c['bitrate'] is not None:
            quality = f"{c['bitrate']}kbps{' VBR' if c['is_vbr'] else ''}"
        elif c['samplerate'] is not None:
            quality = f"{c['samplerate']}Hz/{c['bit_depth']}bit (lossless)"
        else:
            quality = "unknown"
        print(f"{c['username']:<20} {speed_kib:7.1f} KiB/s  {quality:<20} "
              f"slots={c['free_slots']} q={c['queue_size']}  {c['filename']}")

    # 5) Clean up so late replies are ignored and memory is bounded.
    client.searches.remove_request(request)
    return candidates

Transfers — State Machine & Transfer Protocol

The transfer subsystem is the heart of aioslsk: it manages both downloads (files we pull from peers) and uploads (files peers pull from us), drives the SoulSeek peer transfer handshake over the wire, and runs a self-scheduling management loop that auto-retries failed/incomplete transfers and fills upload slots. It is built from four files: transfer/model.py (the Transfer data object + speed bookkeeping), transfer/state.py (a state-design-pattern implementation of every transfer state and its legal transitions), transfer/manager.py (the TransferManager orchestrator and all wire-protocol message handlers), and transfer/cache.py (durable persistence for resume across restarts).

Management Loop & Auto-Retry

The management task is event-driven but self-pacing. request_management_cycle(flag) ORs a flag into _management_flags and pushes a sentinel onto a maxsize=1 queue (a full queue is silently ignored — coalescing) manager.py:535-540. _management_job blocks on queue.get(), snapshots+clears the flags, optionally runs manage_shares_changed(), then always runs manage_user_tracking() and manage_transfers(), finally returning the next interval as min(MIN_TRANSFER_MGMT_INTERVAL + duration, MAX_TRANSFER_MGMT_INTERVAL) i.e. clamped between 0.05s and 0.25s manager.py:517-533, constants.py:34-35. A cycle is requested on: transfer added/removed, any state change (on_transfer_state_changed), AddUser/GetUserStatus responses, session init, successful remote-queue, and PeerUploadFailed.

What gets started. manage_transfers() manager.py:542-567 asks _get_queued_transfers() for eligible downloads and uploads, then: every eligible download gets a _queue_remotely task; eligible uploads up to free_upload_slots get an _initialize_upload task.

Eligibility & auto-retry logic — this is the retry engine, in _get_queued_transfers() manager.py:596-647. It skips OFFLINE users (UNKNOWN gets the benefit of the doubt). For downloads it skips those already remotely_queued, then enqueues a transfer if:

  • state is QUEUED or INCOMPLETE (INCOMPLETE = the auto-resume path after a socket read error), or
  • state is FAILED and fail_reason is None — i.e. only failures with no explicit peer reason are retried; a failure carrying e.g. FILE_NOT_SHARED is not auto-retried manager.py:640-643.

So the auto-retry triggers are: (1) a download dropping to INCOMPLETE on a read error manager.py:1128-1130; (2) a download in reason-less FAILED; (3) PeerUploadFailed clearing remotely_queued so the download re-enters the eligible pool manager.py:1495-1497; (4) the cache loader rewriting interrupted transfers to INCOMPLETE on startup (see below). For uploads, only one queued upload per user is scheduled at a time, and the list is ranked by _prioritize_uploads(): +1 for ONLINE/AWAY, +5 for friends, +100 for privileged users manager.py:649-675.

_queue_remotely manager.py:709-728 sends PeerTransferQueue; on success sets remotely_queued=True and requests another cycle; on ConnectionWriteError/PeerConnectionError it bumps queue_attempts and re-queues (state.queue()) for another try. manage_shares_changed() re-evaluates uploads against block-list/shared status and aborts (reason BLOCKED/FILE_NOT_SHARED) or re-queues them via _evaluate_aborted_state manager.py:569-594,1542-1579.

TransferCache & Durable Resume

TransferCache is a Protocol with read() -> list[Transfer] and write(transfers) cache.py:12-19. Pickling. Durable resume — the startup correction in read_cache() manager.py:147-167: for each cached transfer it first clears remotely_queued = False, then rewrites interrupted states:

  • If it was INITIALIZING at shutdown → re-queue (state.queue()).
  • If it was is_transferring() (DOWNLOADING/UPLOADING) at shutdown → set to COMPLETE if is_transfered(), else INCOMPLETE, and reset_time_vars() manager.py:159-165. The INCOMPLETE state means the management loop will automatically pick it back up and resume from the bytes already on disk.

2. start / run / stop lifecycle (incl. run_until_stopped)

start() (client.py:107) installs the loop exception handler, creates the internal _stop_event, calls load_data() then start() on every service, optionally kicks off a shares scan if settings.shares.scan_on_start (client.py:126), and finally connect()s unless you pass connect=False. run_until_stopped() (client.py:132) simply awaits _stop_event.wait() — it blocks until stop() (client.py:138) sets the event, so it is how you keep a long-running client alive. stop() disconnects the network, cancels every manager's tasks, and writes the transfer/shares caches. The class is also an async context manager (client.py:226): __aenter__ calls start(), __aexit__ calls stop() — but note it does not log you in.

import asyncio
from aioslsk.client import SoulSeekClient
from aioslsk.settings import Settings, CredentialsSettings

settings = Settings(credentials=CredentialsSettings(username="u", password="p"))

async def main():
    # async-with handles start()/stop(); login is still your responsibility
    async with SoulSeekClient(settings) as client:   # client.py:226-231
        await client.login()
        stopper = asyncio.create_task(_shutdown_after(client, 30))
        await client.run_until_stopped()              # blocks until stop() (client.py:132)
        await stopper

async def _shutdown_after(client, seconds):
    await asyncio.sleep(seconds)
    await client.stop()        # sets _stop_event -> run_until_stopped returns (client.py:146-147)

asyncio.run(main())

3. Search, collect results over a window, rank by speed / quality

Use client.searches.search(query) (search/manager.py:114) for a global network search; it returns a SearchRequest (search/model.py:97) carrying a ticket and a growing results list. Each incoming PeerSearchReply is turned into a SearchResult (search/model.py:83) and, when settings.searches.send.store_results is true (default, settings.py:102), appended to request.results (search/manager.py:399); a SearchResultEvent is also emitted (search/manager.py:401). There is no completion signal — results trickle in asynchronously — so you collect over a fixed time window. Each SearchResult exposes avg_speed (bytes/s, search/model.py:90), has_free_slots (search/model.py:89), queue_size (search/model.py:91), and shared_items: list[FileData] (search/model.py:93). Per-file quality comes from FileData (primitives.py:505): filesize, extension, and get_attribute_map() (primitives.py:545) keyed by AttributeKey (primitives.py:71: BITRATE=0, DURATION=1, VBR=2, SAMPLE_RATE=4, BIT_DEPTH=5).

Optionally call client.searches.remove_request(request) (search/manager.py:104) afterwards so late replies for that ticket are dropped.

import asyncio
from aioslsk.protocol.primitives import AttributeKey

async def search_and_rank(client, query: str, window: float = 8.0):
    request = await client.searches.search(query)   # search/manager.py:114
    await asyncio.sleep(window)                      # collect replies for `window` seconds

    # Flatten (result, file) pairs across every peer that replied.
    candidates = []
    for result in request.results:                  # search/model.py:106
        for fd in result.shared_items:              # search/model.py:93 ; primitives.py:505
            attrs = fd.get_attribute_map()          # primitives.py:545
            bitrate = attrs.get(AttributeKey.BITRATE, 0)
            candidates.append((result, fd, bitrate))

    # Rank: free slot first, then peer avg_speed, then bitrate, then filesize.
    candidates.sort(
        key=lambda c: (
            c[0].has_free_slots,   # search/model.py:89
            c[0].avg_speed,        # search/model.py:90  (bytes/second)
            c[2],                  # bitrate (kbps)
            c[1].filesize,         # primitives.py:508
        ),
        reverse=True,
    )

    client.searches.remove_request(request)          # stop accepting late replies
    return candidates  # list[(SearchResult, FileData, bitrate)]; pick candidates[0]

4. Browse a peer folder via PeerGetDirectoryContentCommand

PeerGetDirectoryContentCommand(username, directory) (commands.py:928) sends a PeerDirectoryContentsRequest with a fresh ticket (commands.py:936) and, when executed with response=True, returns list[DirectoryData] from the matching PeerDirectoryContentsReply (commands.py:952). The reply is matched on peer, ticket, and directory (commands.py:946). Peers may silently never reply — there is no protocol-level error for "I won't answer", so the underlying response future would hang. execute() already wraps the wait in async_timeout (client.py:288) using the timeout argument (default DEFAULT_COMMAND_TIMEOUT = 10, constants.py:33), so on no-reply it raises asyncio.TimeoutError. Catch it. Pass the full remote directory path exactly as it appears in a FileData.filename (use the file's parent directory).

import asyncio
from aioslsk.commands import PeerGetDirectoryContentCommand

async def browse_folder(client, username: str, directory: str, timeout: float = 15.0):
    try:
        # response=True -> waits for PeerDirectoryContentsReply (commands.py:941-950)
        dirs = await client.execute(
            PeerGetDirectoryContentCommand(username, directory),
            response=True,
            timeout=timeout,        # client.py:288 wraps the future in async_timeout
        )
    except asyncio.TimeoutError:
        # The peer is offline, firewalled, or simply chose not to answer.
        return []                   # treat "no reply" as empty, never let it hang
    except Exception:
        # send() failures (peer unreachable) also surface here (client.py:282-285)
        return []

    # dirs: list[DirectoryData]; each .name (primitives.py:561) + .files: list[FileData]
    return dirs

5. Download a file to a chosen local_path WITHOUT the race

The trap: client.transfers.download(username, filename) (transfer/manager.py:226) immediately calls add() and then transfer.state.queue() in the same coroutine (transfer/manager.py:237, transfer/manager.py:247). Queuing makes the transfer eligible for the management cycle, which can race to start the actual download before you get a chance to set local_path. If local_path is unset when the file connection arrives, _prepare_download_path() computes a path from settings.shares.download via calculate_download_path() (transfer/manager.py:677-680) — not the one you wanted.

The fix: build the Transfer yourself, add() it (which does not start it — see the docstring at transfer/manager.py:319 and the body, which never calls queue()), set local_path, then queue() it. Transfer identity is (remote_path, username, direction) (transfer/model.py:370), so add() returns the existing object if one matches (transfer/manager.py:332).

import asyncio
from aioslsk.transfer.model import Transfer, TransferDirection

async def download_to(client, username: str, remote_path: str, local_path: str) -> Transfer:
    # 1. add() only registers the transfer; it does NOT queue/start it (transfer/manager.py:319)
    transfer = await client.transfers.add(
        Transfer(username, remote_path, TransferDirection.DOWNLOAD)  # transfer/model.py:76
    )
    # 2. choose the destination BEFORE queueing (avoids calculate_download_path fallback)
    transfer.local_path = local_path                                 # transfer/model.py:85
    # 3. now make it eligible to start (transfer/manager.py:273)
    await client.transfers.queue(transfer)
    return transfer

# Abort (download: cancels tasks AND deletes the partial file via _remove_local_file)
await client.transfers.abort(transfer)        # transfer/manager.py:251 -> state.abort (state.py:252)

# Pause (cancels tasks, keeps the partial file on disk)
await client.transfers.pause(transfer)        # transfer/manager.py:305 -> state.pause (state.py:259)

# Resume a paused/aborted/failed/incomplete/complete download
await client.transfers.queue(transfer)        # transfer/manager.py:273

# Remove from the manager (aborts first, then drops + emits TransferRemovedEvent).
# For a download this also deletes the partial file as part of the abort step.
await client.transfers.remove(transfer)       # transfer/manager.py:346

Watch the local_path reset on re-queue. Re-queueing a download from COMPLETE or ABORTED calls reset_local_vars(), which nulls local_path (state.py:305 in CompleteState.queue, state.py:391 in AbortedState.queue; reset_local_vars at transfer/model.py:171). abort() itself also nulls local_path after deleting the file via _remove_local_file() (state.py:39). So if you re-queue a finished/aborted download to a specific location, re-set local_path after calling queue():

async def requeue_to(client, transfer, local_path: str):
    await client.transfers.queue(transfer)   # may null local_path (state.py:305 / state.py:391)
    transfer.local_path = local_path         # re-assign AFTER queue, before it starts

6. Register event listeners for progress / state / session

Subscribe through client.events.register(EventClass, listener, priority=100) (events.py:125). Critical weakref gotcha: the bus stores listeners as weakref.ref (or weakref.WeakMethod for bound methods) (events.py:130-136). If you register a bare lambda, closure, or a bound method of an object you don't keep alive, it is garbage-collected and silently removed (events.py:211 _remove_callback) — your callback simply stops firing. Keep a strong reference: store the callable (or the owning object) on a variable / instance attribute / a list that outlives the registration.

Useful events: TransferProgressEvent (events.py:601) carries updates: list[(Transfer, prev_snapshot, cur_snapshot)] and fires every settings.transfers.report_interval seconds (default 0.250, settings.py:144) but only when a snapshot changed (transfer/manager.py:220-224). Each TransferProgressSnapshot (transfer/model.py:42) gives state, bytes_transfered, speed, fail_reason, abort_reason. State transitions also drive TransferAddedEvent (events.py:590) and TransferRemovedEvent (events.py:595). Session lifecycle: SessionInitializedEvent (events.py:227, after login) and SessionDestroyedEvent (events.py:234, on disconnect).

from aioslsk.events import (
    TransferProgressEvent, TransferAddedEvent,
    SessionInitializedEvent, SessionDestroyedEvent,
)

class TransferWatcher:
    """An owning object that holds strong refs so listeners are NOT GC'd."""
    def __init__(self, client):
        self._client = client
        # register bound methods; keep `self` alive for them to keep firing
        client.events.register(TransferProgressEvent, self.on_progress)   # events.py:125
        client.events.register(TransferAddedEvent, self.on_added)
        client.events.register(SessionInitializedEvent, self.on_session)
        client.events.register(SessionDestroyedEvent, self.on_session_gone)

    async def on_progress(self, event: TransferProgressEvent):
        for transfer, prev, cur in event.updates:   # events.py:610
            print(transfer.remote_path, cur.state.name,
                  cur.bytes_transfered, f"{cur.speed:.0f} B/s")  # transfer/model.py:42-58

    async def on_added(self, event: TransferAddedEvent):
        print("added:", event.transfer)

    async def on_session(self, event: SessionInitializedEvent):
        print("session up:", event.session.user.name)

    async def on_session_gone(self, event: SessionDestroyedEvent):
        print("session gone")

# WRONG: lambda is GC'd immediately after register() returns -> never fires.
# client.events.register(TransferProgressEvent, lambda e: print(e))   # weakref'd away

This is a soulshelf fork (pyproject still reports v1.6.3). The only functional divergences from upstream are six logging-level downgrades from warning/error to debug, all motivated by the fact that on a NAT'd, firewalled, leech-only P2P client these conditions are expected churn rather than actionable problems — at upstream levels they flood the logs.
